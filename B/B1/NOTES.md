# B1：异常、上下文与 RT-Thread

范围取自固定的 v26.07 B1 原文，以及其链接的 PA3 阶段 1、PA4.1 到 RT-Thread 启动为止。后续 Nanos-lite、用户进程、虚拟内存不在这次范围内。硬件实现 RV32E 与机器模式同步 ECALL；独立 NEMU 使用 RV32IM。没有实现异步抢占、中断控制器或 U/S 模式。

## 为什么保存完整上下文

函数调用遵循 ABI，调用方和被调用方分担寄存器保护。异常入口不能假定被打断处恰好满足函数调用的保存约定；它还要保存恢复执行所需的 PC 和状态。因此本实现保存所有 GPR 槽位、`mcause`、`mstatus`、`mepc` 和地址空间占位指针。

`Context *c` 指向当前线程栈上的一段内存。它不是 C 处理函数临时分配的对象：`trap.S` 先减小 SP，为整个结构预留空间，再用 `sw` 逐项填充，最后把 SP 放入 `a0` 作为 C 函数的第一个实参。C 头文件描述这段内存的布局，汇编实现这个布局；静态断言检查两者的一致性。

| 字段 | RV32E 字节偏移 | RV32I 字节偏移 | 谁写入 |
|---|---:|---:|---|
| `gpr[0]` | 0 | 0 | 汇编写零 |
| `gpr[n]` | `4n` | `4n` | 汇编保存寄存器；SP 保存减栈前的值 |
| `mcause` | 64 | 128 | 硬件/NEMU 先写 CSR，汇编读 CSR 后入栈 |
| `mstatus` | 68 | 132 | 同上 |
| `mepc` | 72 | 136 | 同上；AM 对 ECALL 的返回地址加 4 |
| `pdir` | 76 | 140 | 写零，当前没有地址空间切换 |
| 总大小 | 80 | 144 | 均满足 16 字节栈对齐 |

## 从 yield 到返回的完整路径

1. `yield()` 把系统调用号寄存器设为全 1：RV32E 用 `a5`，RV32I 用 `a7`，再执行 ECALL。它与普通系统调用共享异常入口，AM 通过这个值区分 `EVENT_YIELD`。
2. NEMU 的 `isa_raise_intr(11, pc)`，或 RTL 的异常分支，把当前 ECALL 地址写入 `mepc`，把 11 写入 `mcause`，将 MIE 复制到 MPIE 并清 MIE，跳到 `mtvec` 的基址。即使 `mtvec.MODE=1`，同步异常仍跳到基址。
3. `trap.S` 按上表保存所有寄存器。先保存 `t0`，再把它用作 CSR 搬运临时寄存器，避免覆盖原来的 `t0`。保存 `gp` 使新线程能使用程序的数据访问约定。
4. `mv a0,sp; call __am_irq_handle` 进入 C。处理函数将 cause=11 且调用号=-1 的异常封装为 YIELD，令保存的 `mepc += 4`，调用注册的回调。ECALL 保存的是自身地址；漏加 4 会重复执行 ECALL。这个规则不能泛化到需要重试故障指令的异常。
5. 回调可以返回原 `Context *`，也可以返回另一个线程的上下文。汇编执行 `mv sp,a0`，因此后续恢复的数据由回调选择。
6. 汇编先恢复 `mstatus`、`mepc`，再恢复 GPR，最后恢复 SP。`mret` 跳到 `mepc`，将 MPIE 复制到 MIE，并置 MPIE。该设计只实现 M 模式，MPP 保持 M。
7. 恢复原上下文时，ECALL 后的指令继续运行；切换到新上下文时，执行 `kcontext()` 预置的入口，`a0` 已是线程参数。

`kcontext()` 只清零并填写一个 Context；不会在其栈区额外写入线程参数块。RT-Thread 的 `rt_hw_stack_init()` 在调用 `kcontext()` 之前，单独放置入口、参数、退出函数三元组。两个线程各持有自己的这份数据，连续创建线程不会覆盖先前入口。线程入口返回后由启动包装函数调用 RT-Thread 的退出函数，避免直接返回到无效地址。

当前 `switch_from/switch_to` 的全局交接槽只用于单核、无异步中断的同步切换：异常处理函数在恢复下一上下文前清空它们。这个前提下不存在并发覆盖；若添加抢占或多核，就必须改为线程私有交接信息或适当的同步机制，不能直接沿用这个实现。

## mcycle 与参考模型

`mcycle=0xb00`、`mcycleh=0xb80` 表示同一个 64 位计数器的低/高半部。每个 CPU 上升沿增加 1，包含访存等待周期；显式 CSR 写入优先于该次增量。软件按“高—低—高”读取，前后高半部不同则重读，避免低半部溢出时拼出错误值。

SoC DiffTest 每个 CPU 周期推进 NEMU 的独立计数器模型，在指令退休时比较所有 GPR 和 PC。没有把 DUT 的计数值拷入参考模型。时钟观察器记录上升沿实际采样到的 reset，再在观测阶段推进参考时钟，避免框架复位释放造成一周期偏差。冻结参考时钟的反例会在 CSR 读取处发生 DiffTest 不一致。

原 Spike 适配器开启 U/S 模式，其 MPP 初值和 MRET 行为与本项目不同。B 的适配器明确设为 RV32IM、仅 M 模式、初始 `mstatus=0x1800`，没有修改 Spike 的指令语义，也没有跳过 CSR 比较。这符合 [RISC-V 机器模式规范](https://docs.riscv.org/reference/isa/priv/machine.html) 对未实现 U 模式时 MPP 的规定。适配器、原库指纹及首次失败日志均有记录。

`mvendorid=0x79737978`，`marchid=0x26070001` 是本地工程标识，并在进入 main 前输出；不是学号，不代表官方申请或考核身份。

## 已运行的检查与复验

- 独立 NEMU：16 次 yield；两个独立栈的 52 次切换；32 个寄存器槽、线程参数、栈局部变量；破坏 t0 恢复必须返回 95；原始 RT-Thread 内置命令及线程返回测试。普通指令逐条与配置一致的 Spike 比较，MMIO 同步计数独立记录。
- NPC/完整 SoC：mcycle 单调递增、低半部溢出、高半部 CSR 操作、错误参考时钟拒绝；RV32E 的 52 次上下文切换和 t0 破坏反例；Flash 启动并搬运至 SDRAM 后运行 RT-Thread。
- `etrace.jsonl` 由 NEMU 在 ECALL/MRET 时记录，不在被测程序内插入 printf。它保留 PC、目标地址、cause、epc、status，便于核对入口和返回配对。

结果在 `reports/B1_native.json` 与 `reports/B1_npc.json`，命令、输入哈希、stdout/stderr、返回码和内存采样在 `artifacts/B1`。原始十条 shell 命令后附加了上下文测试和明确的结束命令，所以这些运行有可判定的终点；不把超时当作启动成功。

在项目目录运行：

```powershell
wsl -d YSYX-Linux -u ysyx -- python3 /workspace/projects/ysyx_f_to_b/B/B1/verify.py native
wsl -d YSYX-Linux -u ysyx -- python3 /workspace/projects/ysyx_f_to_b/B/B1/verify.py npc
```

这证明所记录程序和反例的行为，不是完整特权架构、任意线程程序或异步抢占的证明。

## PA 来源中的补充问题与范围

PA3 的上下文必答题已在前面逐步展开。下面记录其余相关思考，不把其它 ISA 的示例当作本项目实现。

| 来源问题 | 回答与适用条件 |
|---|---|
| 为什么异常保存这些状态 | 必须保存恢复执行所需的指令位置、特权/中断状态，以及分辨处理原因的信息。寄存器名字随 ISA 改变，责任相同。 |
| 用软件模拟未实现指令 | 非法指令陷入后，处理程序可解码原指令、计算结果、修改保存的 GPR/PC；但本项目没有实现浮点仿真，也不据此允许 AM 浮点或栈越界等 UB。 |
| cause 能否完全由软件保存 | 入口处可以把硬件原因复制到栈中；但统一异常入口仍需要可靠的原因来源。只观察 PC 无法普遍区分访问故障等所有原因，不能直接删去 cause 的职责。 |
| 异常和函数调用是否相同 | 函数调用受 ABI 约束，调用双方合作保护状态；异常可出现在任意指令处，入口必须保存被打断程序后续会使用的全部状态，返回还需要恢复异常 PC/状态。 |
| `pushl %esp` 的含义 | 在该 x86 示例中，把压栈前的 ESP 值再压入栈，作为已构造上下文的地址传给 C。需要按该 ISA 的 PUSH 语义和调用约定读代码，不能直接套用 RISC-V 的寄存器传参。x86/MIPS 不做本轮实现验收。 |
| 为什么不能对所有异常返回 PC 加 4 | 当前 ECALL 是固定 4 字节，返回时跳过它；故障修复后可能需要重试原指令。变长 ISA、分支延迟槽还要保存各自的返回语义，不能统一加常数。本项目没有 RVC 或 MIPS 延迟槽。 |
| 多个程序为何不能直接放到不同物理地址 | 固定链接地址决定了代码和数据引用；随意搬运会使绝对地址失效。需要重定位、位置无关代码或虚拟地址等机制，当前 B1 不扩展到 Nanos-lite 用户进程加载。 |
| 为什么线程要有独立栈 | 返回地址、局部变量和保存的上下文都在栈里。共享同一栈位置会互相覆盖，即使切回正确 PC 也无法继续原来的调用链。 |
| 为什么称线程而非进程 | 此处执行流共享一个地址空间，仅有独立栈和寄存器上下文；通常将这种执行实体称为线程。进程通常同时包含资源与地址空间的隔离概念。 |
| 机制与策略如何分开 | CTE 提供创建、保存和恢复上下文的能力；调度器决定下一次选择谁。改变轮转策略不应重写 trap.S 的保存布局。 |
| RISC-V 参数如何传入新上下文 | 新线程入口的第一个参数放在 a0，SP 满足当前 ABI/实现的对齐要求。RV32E 可用参数寄存器少于 RV32I；本实现的 Context 统一按 16 字节对齐，两个布局各有静态检查。 |
| 连续建线程为何不能用一个全局入口参数 | 第二次创建会覆盖第一次尚未使用的参数。当前实现把入口、参数、退出函数放到各线程自己的栈中，再让 kcontext 只创建 Context。 |
| 全局切换槽在抢占或多核下为何危险 | 两个切换请求可能交叉覆盖 from/to。当前单核同步路径有明确串行前提；扩展时应把交接信息放到各自栈帧或线程控制块，并处理同步，不能拿现有通过记录证明并发安全。 |
| 不用全局变量如何交接 | 将切换参数放在当前调用栈或上下文中，通过约定寄存器/Context 指针传给异常处理程序；异常返回再选目标 Context。需要同时修改调用方与处理方的约定。 |
| 多个 AM 程序直接链接会有什么问题 | 重名符号、各程序的初始化数据/BSS 和运行状态会冲突。原集成脚本用 objcopy 添加应用符号前缀、重定向共享服务、汇总段；启动应用时恢复 data 并清 BSS。脚本位置为运行包中 `rt-thread-am/bsp/abstract-machine/integrate-am-apps.py`。 |

“在 RT-Thread 上运行 AM 程序”是启动之后的蓝框扩展。B1 明确止于启动 RT-Thread，因此本轮 B1 镜像关闭应用集成；旧 C 阶段的真实应用/GUI验收保留，不冒充新流水线的应用集成验收。PA 来源保留完整页面以便查阅，完整页面中的后续内容不自动扩张 B1 的任务边界。操作系统定义、侧信道攻击和二周目阅读项仅作背景范围登记，没有宣称逐篇复现其安全研究。
