## 0–2：环境、编译产物与Make

Linux环境、普通用户ysyx、GCC/Make/GDB/Git/Valgrind已实际运行正反例。用Vim的普通文本模式给练习6补上缺失的井号，保存结果与经过验证的修正版字节相同；用二进制模式编辑一份ex1可执行文件副本，仅改变ELF头的一个字节，随后执行被拒绝，退出126。原始源码和正常可执行文件都保留。另一个固定种子的二进制变异也已运行。

练习1的原始代码缺少stdio.h，在当前GCC上产生隐式声明警告，仍输出Hello world。修正版显式包含头文件，严格编译无警告，Valgrind也未报错。额外版本实际多打印五行。编译器认识某个内建函数不代表C允许随意省略声明；应让函数声明和调用类型一致。

Make实验实际执行了默认all、clean以及清理后的重新构建，覆盖ex1和ex3。改进版用PROGRAMS变量维护产物列表，并声明all和clean为.PHONY。删除配方行的TAB后，make报告missing separator并退出2。这里的PASS表示负对照被正确拒绝。书中Markdown显示的等宽空白不等于实际TAB，工作Makefile按原文明确说明使用TAB。

实际阅读的man puts、man make、man gcc/man cc原文保存在对应stdout.log。-g保留调试信息；-Wall启用一组常见警告，并不等于编译器存在的所有警告。文件名、依赖、构建配方及默认目标的含义，也与[GNU Make官方手册](https://www.gnu.org/software/make/manual/make.html)核对。

另一个实际C项目选用已归档NEMU。其根Makefile首先检查NEMU_HOME，读取menuconfig生成的变量，合并filelist.mk，再剔除黑名单源码；默认目标是app。scripts/build.mk把C/CC源文件映射成build下的.o，以-MMD生成依赖文件，最后通过C++链接器链接。-include允许尚不存在的依赖文件；$<是当前首个依赖，$@是目标。这项只要求阅读理解，未冒称已经构建NEMU。源文件位于/workspace/YSYX_F_B_Archive/repos/NJU-ProjectN__nemu__ics2024。

## 3：格式串、转义与错误复现

标准输出已逐字节核对：年龄10、高度72。故障实验包括漏传参数、未初始化age，以及把整数作为字符串地址传入。它们产生了编译诊断、未初始化值报告或SIGSEGV；漏传参数的某次执行没有触发Valgrind错误，不能据此判为正确。

printf不会替调用者自动把类型改成格式串需要的类型。常用转换包括：d/i有符号整数，u/o/x/X无符号整数，f/F/e/E/g/G/a/A浮点，c字符，s字符串，p指针，n写出当前输出计数，以及%%输出百分号。-、+、空格、#、0是常用标志；宽度和精度可用数字或星号指定；hh、h、l、ll、j、z、t、L指定相应长度/类型。细节以实际保存的printf(3)及[glibc格式输出文档](https://sourceware.org/glibc/manual/latest/html_node/Formatted-Output.html)为准。

supplement.c实测八/十六进制、前缀、补零、左右对齐、字符串截断、空字符串、浮点精度、十六进制浮点、各整数长度以及受控的%n。测试使用固定格式串，并严格比较snprintf结果。

C字面量的转义由语言处理，printf处理百分号转换。常见转义为\a、\b、\f、\n、\r、\t、\v、\\、\'、\"、\?，以及八进制、十六进制和通用字符名形式。书中把\r解释成TAB是错误的：\r是回车，\t才是水平制表。实验以实际字节比较了TAB、LF和CR，没有用终端显示效果代替字节检查。

## 4：Valgrind、源码与另一个手工构建

原始ex4故意漏传age且未初始化height。编译器与Valgrind实际报告了相应问题，工具按--error-exitcode=99返回99。修正版补齐参数、把height初始化为72，输出符合预期，Valgrind报告0错误。GDB和另一个堆越界/泄漏反例也在环境验收时真实运行。[官方Memcheck入门](https://valgrind.org/docs/manual/quick-start.html)用于核对调试信息和错误定位方法。

另一个手工构建的程序是Vim官方仓库中的xxd。通过GitHub工具取得原始C文件和Makefile，核对Git blob SHA及本地SHA-256，用Linux make -j1构建，实测版本xxd 2026-06-16。对包括0..255全部字节、NUL和0xff的262字节输入，检查输出等于Python独立计算的十六进制，再反向还原并逐字节比较。未运行上游clean中的递归删除命令，也未把它安装到系统默认路径。

Valgrind3.18.1源码通过Ubuntu的APT源码索引取得，原始包与发行版补丁包都与.dsc的SHA-256相符。已保存并阅读README、Makefile.am、Makefile.in及许可证。顶层结构实际包含VEX、coregrind、memcheck、cachegrind、callgrind、helgrind、drd、massif、dhat、include、tests及docs等。

Makefile.am的SUBDIRS先安排include、VEX和coregrind，再构建工具、共享内容、测试和文档；原文件明确把较慢的文档放在末尾。它还定义默认抑制规则、版本头、regtest与perf等目标。Makefile.in是配置模板，configure会生成实际Makefile。续跑后使用 `--enable-only64bit`、`make -j2`、私有前缀安装完成；源码构建的绝对路径工具实际检验20,000次链表操作零错误，并检出故意越界和17字节泄漏。此结论限定本机AMD64构建，不声称32位或其它架构已测试。旧RESOURCE_LIMIT记录保留为历史。

## 5：逐项解释C程序结构

| 符号/语句 | 含义与核对 |
|---|---|
| #include <stdio.h> | 预处理包含头文件，提供声明和类型；不是运行时函数调用。 |
| /* ... */ 与 // | 注释；前者跨行，后者到行尾，不是可执行语句。 |
| int main(...) | 宿主C程序的入口函数接口；运行时启动代码最终调用它，CPU并不按名字寻找main。 |
| int argc | 参数数量；程序名通常也在参数序列中。 |
| char *argv[] | 参数位置中的数组形式调整为指针，元素又是字符指针；字符串并非内嵌在指针变量中。 |
| { ... } | 复合语句及作用域边界。 |
| int distance = 100; | 声明一个int并初始化；不能把未初始化对象当成已经为0。 |
| = | 赋值/初始化中的符号，和比较用的==不同。 |
| printf(...); | 调用变参函数，格式串必须与后续参数类型相符。 |
| &、*、[] | 分别涉及取地址、指针声明/解引用、按元素索引；具体含义由语法位置决定。 |
| ; | 结束相应声明或语句；不是所有花括号后都需要加分号。 |
| return 0; | 结束main并向宿主运行环境报告成功。 |

对前面ex1–ex4也应用了同样的分解：声明先于调用，变量在使用前初始化，变参类型一致，退出码和程序输出分开核对。这里没有编造“不认识的符号”；未解释清楚的项目应作为开放问题保留。纸上记录改为可审阅的Markdown，未声称人类已经完成手写训练。

## 6–7：类型、提升、取值范围

练习6原始代码第一行少了#，已先实际复现编译失败，再在副本修复。交换first_name与initial会把整数当地址，Valgrind实际给出非法读和SIGSEGV。float作为变参会提升成double，char等小整数会进行整数提升；格式符仍须按提升后的类型选择。

练习7原文省略stdio.h；保留原版警告和输出，另存显式声明的版本。原程序输出1073741824及120.000000，指数比例与参考一致。对实际universe_of_defects分别试验1、1024、LONG_MAX、过大的有符号字面量和过大的无符号字面量。比例计算显式转为double，承认大整数转换可能舍入；整数打印值单独严格核对。超出范围的字面量是诊断/结果观察，不写成跨编译器保证。

正常的无符号运算按2的类型位宽次方取模；实测ULONG_MAX加1得到0。与此不同，有符号乘法溢出由UBSan检出。[GNU C无符号运算说明](https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Unsigned-Overflow.html)支持这一规则。char是整数类型，乘法前会提升，因此100乘空字符0得到0；这不意味着char与int的存储大小相同。

把整数0传给%s在这一次glibc执行中打印了特殊结果，且Valgrind未报错；仍不能把错误参数类型当成合法C。编译诊断和动态工具的覆盖范围不同。

## 8–9：数组、字符串与内存图

原始sizeof输出在当前Linux平台符合书中数字；修正版用%zu匹配size_t，而非依赖%ld与size_t恰好同宽。额外实验实际给数组元素赋值、把字符值放进int数组、把字符按十进制和十六进制打印，并检查结果。

实际ABI对照：

| 实测目标 | int | long | 指针 | CHAR_BIT |
|---|---:|---:|---:|---:|
| Windows x86-64 / MinGW GCC | 4字节 | 4字节 | 8字节 | 8 |
| Linux x86-64 / GCC | 4字节 | 8字节 | 8字节 | 8 |

因此不能只凭“64位CPU”猜long或int的大小。[Microsoft类型范围](https://learn.microsoft.com/en-us/cpp/cpp/data-type-ranges?view=msvc-170)描述了其Windows编译器模型；本机MinGW行是独立实测值。[RISC-V ABI文档](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/)也区分ILP32与LP64。本节点没有运行RISC-V交叉编译，查询的在线ABI文档为开发快照，不当作已实现的扩展认证。

    another（指针变量，实测8字节） ---> 字符串字面量 [Z][e][d][\0]

%c输出NUL时仍产生一个0字节，终端只是通常不显示它。原始stdout按字节核对，未把这些0字节截掉。字符串必须有可达的终止字符，字符数组未必是字符串。

把char数组元素用%d打印会发生合法整数提升，不必产生警告或Valgrind错误。把char存储强行当作int指针读取则另有对齐、有效类型和越界风险；实验用UBSan检出了特意构造的未对齐读。安全的对象表示复制采用memcpy，实测Zed加终止字节对应小端数值0064655a，回拷后四字节一致，未用违反别名规则的指针强转。

把name改成指向字符串字面量，保留后续写入操作，会在本次Linux上触发SIGSEGV。改成指向可修改复合字面量数组则正常，并通过Valgrind。原文“char*形式产生相同东西”的表述需要限定：字符内容可以相同，存储对象、可写性和sizeof不相同。

## 已实际观察到的工具边界

移除栈数组/全局数组终止符、越界下标等案例，Valgrind多次报告0错误，但ASan均报告了相应越界。这不是修改坏程序使检查器通过，而是保留坏程序，分别记录两个工具的真实诊断。无警告、未崩溃、Valgrind零错误都不能单独证明C程序正确。

WSL直接执行发生SIGSEGV的程序时，本次Windows进程退出码为11；经shell包装常见的是139。检查器兼容两种传递形式，并要求日志明确包含SIGSEGV。未初始化数组也不保证被当前编译器静态警告捕获；对应实验仍严格要求Valgrind报告未初始化值。
