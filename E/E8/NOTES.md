# E8：四值、网表和物理实现的证据链

本阶段依据锁定讲义 `sources/E8.md`；相对引用可从[原始归档](https://ysyx.oscc.cc/docs/2607/e/8.html)浏览。物理设计对象仅为 CPU 顶层 `ysyx_00000000`，不包含课程 SoC、GPIO 或仿真存储器。各项实际完成状态以相应 JSON 报告为准；本说明不代替签核结果。

## 前端检查为什么放在布局之前

硬件错误经过布局布线后更难定位。先检查地址位宽、时钟边沿、锁存器、复位和网表功能，可以把这些错误排除在漫长的物理流程之前。

CPU 的取指和访存地址输出均保留完整 32 位。外部仿真存储器对未建模地址报错，不代表 CPU 拦截地址。本阶段用独立总线测试覆盖高位、区域边界、字节通道以及 `0xffffffff` 等 16 个地址，并用故意截断高地址的变体验证检查器。16 个测试点不是穷举全部 $2^{32}$ 个地址，接口连线和位宽还需静态核对。

可综合 CPU 状态只在上升沿更新。测试平台在另一时刻采样或驱动信号是仿真安排，不应混入 DUT 的时钟结构。综合实例中检查 `LAT*` 等锁存器；仅凭 RTL 中没有写 `latch` 这个词不足以证明不会综合出锁存器。

`--lint-only -Wall` 用于检查自写 RTL。提供的 SoC 和标准单元模型会有另外的工具兼容警告，不能借由对这些第三方文件使用兼容选项，推导出自写代码也已无警告。

## 四值仿真观察的是什么

Verilator 的常用二值仿真会给未初始化信号一个具体 0/1 值。这样，遗漏复位的状态寄存器可能恰好落在合法状态。Icarus 的 `X` 初值能暴露这类缺陷。

负对照只去掉状态机复位：默认二值仿真能够跑过小程序，四值仿真则在总线控制出现 `X` 时失败。另有缺失 VPI 插件、未知访存参数、错误退出值等对照。不能把 `X` 转成 0，也不能用无条件初始化来让错误变体通过。

这里的四值范围是 CPU RTL 或标准单元网表的信号状态。VPI 外部存储器模型提供已知二进制数据；没有声称验证了任意未知外部 RAM 内容、模拟亚稳态或所有输入轨迹，也没有把这些程序运行等同于形式化证明。

## VPI 怎样连接内存

Icarus 使用 VPI 注册系统任务和函数：初始化装载程序，读取地址与访问类型，执行写入，更新模拟周期，最后保存状态。取参使用 `vpiVectorVal`，检查每个字的 `bval`；发现 `X/Z` 立即记录失败。只取 `aval` 会悄悄丢失不定态信息，是这个接口特别容易犯的错误。

复位 PC 保持 `0x30000000`。外部 Flash 模型在最前面提供两条跳转指令，转入 `0x80000000` 的 AM 程序。这样不必为门级测试另改 CPU 复位逻辑。

门级网表没有 GPR 调试端口，因此无法沿用 RTL 的逐指令寄存器比较。AM 的测试副本在原 `ebreak` 前向 `0xf0000000` 写退出码；基准算法、校验和与通过条件保持。测试平台同时检查唯一一次退出写、退出码、随后取到的 `ebreak`、总线安静窗口和原程序的 PASS 输出。这是端口行为与程序自校验的联合证据，不描述为从网表读取了架构提交状态。

## 为什么必须使用同一工艺库的单元模型

综合网表描述的是标准单元实例与连接关系。只有结合对应工艺库的行为模型，仿真器才知道每个单元如何响应输入。这里使用锁定 ICsprout55 v1.10.100 的原始 R/L 单元文件。

Verilator 采用课程要求的 `functional` 和 `__VERILATOR__` 宏。最终 Icarus 网表运行仅定义 `functional`，保留库中的原始 UDP 触发器模型。没有为了减少运行时间改写触发器真值表。

最初 Icarus 11 的完整 microbench 达到 1800 秒 CPU 预算，被记为 `RESOURCE_LIMIT`。这个结果既不是程序失败，也不是通过。对比已安装版本后，Icarus 14 的 hello 更快，最终完整任务改用它，并提高时间预算。额外进度日志只记录周期和 UART 行，不改变存储器或 DUT 行为。官方行为分支在本机反而更慢，未用于最终四值资格检查。

最终用于后端的候选是 BALANCE 基线网表；AREA 候选用于 E7 的面积/频率比较。两个策略的额外小例测试不能替代最终候选的完整 hello、microbench 运行。

## 物理设计每一步回答不同问题

| 环节 | 主要作用 | 不能单独推出的结论 |
|---|---|---|
| Floorplan、放置 | 确定核心区域、行、管脚和单元位置 | 不说明所有连线已经合法 |
| CTS、合法化 | 构建时钟树、修正单元重叠与行对齐 | 不说明所有时序角都满足约束 |
| 布线、DRC | 生成连线并检查设计规则 | DRC 干净不等于逻辑连接正确 |
| LVS | 核对版图与网表连接一致性 | 不替代功能仿真或时序检查 |
| RCX、STA | 提取寄生，检查多角 setup/hold | 布局前 TT 频率不能代替该结果 |
| filler、Harden、签核包 | 补齐物理结构，导出集成所需数据 | 导出文件存在不等于实际流片或官方验收 |

工程通过 ECOS Studio 同一后端的 ECC 工作区接口创建和运行流程，再调用实际签核检查器。仅有综合结果的工作区已经作为负对照，签核器正确阻止导出。最终只有全部必需文件、流程状态和质量门槛满足后才允许导出；没有宏单元时缺少宏坐标属于讲义解释的提示项。

如果目标频率过高，可以新建较低频率的工作区；如果布局布线拥塞，可以调整利用率。它们改变设计目标，必须保留每次约束及结果，不能把降低约束后的通过写成原目标通过。

本机先用小计数器检验完整后端路径，再做 CPU。绘图阶段的并发内存峰值曾触发保护，相关记录保留为资源限制。用户随后授权更多内存；WSL 由 2 GiB 调整为 4 GiB 的实际生效情况另记于 `E_backend_memory_update.json`。线程、进程组内存和可用内存仍受监控，不修改 DRC、LVS 或 STA 判定。

## 复验入口与证据边界

`preflight.py`、`address_test.py`、`rtl_icarus_programs.py`、`mapped_preflight.py`、`mapped_final.py` 分别覆盖接口/四值小例、地址复位、RTL 完整程序、小型网表对照和最终完整网表程序。`prepare_physical.py` 与 `physical_run.py` 管理后端工作区，`E/runtime/ecc_rpc.py` 使用公开的 JSON-RPC 协议。

报告记录实际退出码、运行输入和哈希。输出目录中即使出现 GDS，也要检查整步是否结束、完整流程是否成功、签核器是否允许导出。前一次进程中断或资源超限留下的半成品不能当作通过证据。最终成果是本地工程与所记录条件下的验证，不等于个人入学通过、课程官方认可或已经生产的芯片。
