# D1：从 C 源码到真正执行

本章依据 [D1 原文副本](sources/D1.md)完成 16 项核心实验。输入文件在 [src](src)，编译器输出在 [results](results)，每个命令的版本、退出码、输入输出哈希和日志在工程 `artifacts/D1`。结果摘要见 [D1_experiments.json](../../reports/D1_experiments.json)。本说明是独立解释与实测，不是官方参考答案。

## 1. 识别当前处于哪一个编译阶段

看到 `.c`，先问“头文件和宏有没有展开”；看到 `.ll`，问“这是 LLVM 的中间表示还是处理器指令”；看到 `.o`，问“符号地址和外部引用是否已经确定”；看到 ELF，则问“它针对哪一种 ISA、从什么入口开始”。这样不会把能编译、能链接、能在本机执行误认为同一件事。

```mermaid
flowchart LR
  C[C 源文件] -->|预处理| I[展开头文件与宏]
  I -->|词法、语法、语义分析| AST[语法树]
  AST --> IR[LLVM IR]
  IR -->|优化、目标代码生成| ASM[RISC-V 汇编]
  ASM --> OBJ[目标文件及重定位]
  OBJ -->|链接运行时和库| ELF[ELF]
  ELF -->|装载、启动代码| MAIN[main]
  MAIN --> EXIT[运行时清理与退出系统调用]
```

实际执行的 `clang -ccc-print-phases`、token 和 AST 输出分别在 `artifacts/D1/clang_phases`、`clang_tokens`、`clang_ast`。编译阶段的语义也可查 [Clang 官方命令说明](https://clang.llvm.org/docs/CommandGuide/clang.html)。本地使用锁定的 Clang 15；网页当前版本不作为本地版本证明。

## 2. 预处理与头文件选择：M001–M004

输入 [preprocess.c](src/preprocess.c)同时使用换行拼接、注释、条件编译、字符串化和标识符拼接。`MSG` 最终成为 `"Hello World!\n"`；注释消失；`_concat(pr,intf)` 变成 `printf`；`_str(RISC-V)` 产生字符串。

宿主的 [host.i](results/host.i)没有条件分支中的问候语；[riscv.i](results/riscv.i)包含 `Hello RISC-V!`，因为交叉编译器预定义了 `__riscv`。两份输出均包含 `# 行号 "文件"` 标记，供后续诊断回溯原文件。这些标记不是程序中的函数调用。

`gcc -E -v` 的 stderr 给出了真实搜索目录。`-I src/include` 把自建头文件排在标准搜索路径之前，[custom.i](results/custom.i)中的 `2607` 来自自建头的宏。去掉 `-I` 后，专门的 `#error wrong header selected` 触发编译失败，证实正例确实选中了任务目录的头文件；系统 `stdio.h` 未修改。

| 预定义宏 | 宿主 GCC | RISC-V GCC 默认目标 |
|---|---|---|
| `__x86_64__` | 1 | 未定义 |
| `__riscv` | 未定义 | 1 |
| `__riscv_xlen` | 未定义 | 64 |
| `__SIZEOF_POINTER__` | 8 | 8 |
| `__LP64__` | 1 | 1 |
| `__BYTE_ORDER__` | 小端 | 小端 |

默认交叉目标是 RV64 Linux，不能因为工具名含 RISC-V 就把输出称为 RV32E。后面 NEMU/NPC 裸机程序会明确使用 RV32IM/ILP32 或 RV32E/ILP32E。

## 3. IR、优化和 volatile：M005–M007

[add.c](src/add.c)先初始化 `x=10,y=20`，然后相加并打印。未优化的 [O0.ll](results/O0.ll)保留栈空间、存储、读回和 `add nsw i32`；优化后的 [O1.ll](results/O1.ll)将可推导的结果直接变成传给 `printf` 的常量 30。

判断依据是输出文件中的实际操作，并非预先规定某个编译器必须产生固定字符串以外的特定寄存器分配。`nsw` 是与有符号溢出语义相关的 LLVM 标记，不表示硬件自动检测所有溢出。

给两个局部变量添加 `volatile` 后，[volatile_O1.ll](results/volatile_O1.ll)仍有 `store volatile`、`load volatile` 和相加。编译器必须保留这些可观察访问；这不使操作变为原子操作，也不建立线程间同步关系。

三个背景问题的关键是可观察效果和可见性：

- 被覆盖的赋值可以消除，但 `f()` 可能输出、修改全局状态或不返回，不能仅凭“返回值无用”删除调用。
- `f2(x)` 的参数虽然循环不变，其副作用和结果未必循环不变；只有满足相应语义条件，才能把调用提到循环外。
- 某函数在当前文件中只有一个调用点，不意味着其他目标文件不会调用它。[visibility.c](src/visibility.c)的 `public_add` 在 `-O2` 目标文件符号表中保留，内部可见的 `local_add` 被内联后消失；这是本次工具配置的观察。

## 4. 汇编、重定位与可执行文件：M008–M011

对照 [rv64-O0.s](results/rv64-O0.s) 与 C 程序：函数序言建立栈帧；常量装载和保存对应局部变量初始化；读回与 `addw` 对应加法；参数寄存器与 `call printf` 对应格式化输出；尾声恢复状态并返回。[rv64-O1.s](results/rv64-O1.s)直接准备 30，减少局部变量访问。

目标文件还不能独立运行。`objdump -dr` 中，外部调用及地址引用旁有 RISC-V 重定位项；链接后 ELF 分配了代码/数据地址，加入 `_start`、运行时和动态链接所需结构。动态链接 ELF 仍可能保留由装载器解析的重定位，不能笼统说“链接后不存在任何重定位”。

本次先遇到 GNU 汇编器不认识 Clang 输出中的 `.addrsig`。保留该失败日志后，改用 Clang 自身的集成汇编器生成目标文件，再由 RISC-V GCC 链接；没有删除错误诊断或手改指令以掩盖不兼容。

这些 ELF 的机器类型是 RISC-V，不在 x86 宿主上直接执行。本章的执行与计时使用另行编译的 x86 程序。

## 5. 优化等级与实测耗时：M012

[sum.c](src/sum.c)计算 `1+2+…+100000000`，三种优化等级的结果均为 `5000000050000000`。使用无符号 64 位累加，并对过大的输入返回非零；当前范围内没有算术溢出。终值从命令行输入，使实验不依赖把整个常量表达式提前算完。

| GCC 等级 | 三次墙钟时间 / 秒 | 中位数 / 秒 |
|---|---|---:|
| `-O0` | 0.290、0.306、0.296 | 0.296 |
| `-O1` | 0.089、0.104、0.061 | 0.089 |
| `-O2` | 0.054、0.052、0.059 | 0.054 |

时间由同一运行记录器测量，包含进程启动、输出与主机调度开销。它们是这台机器、这次负载的观察，不是 ISA 时钟周期或跨机器性能保证。反汇编显示优化后减少了低效的栈读写。不能推论“优化等级越高，任意程序一定越快”；`-Ofast` 的语义放宽也不能当作普遍正确的等价优化。

## 6. main 前后发生了什么：M013–M014

[startup.gdb](src/startup.gdb)从 `starti` 停在动态装载器入口开始，随后命中程序的 `_start`，再命中 `main` 的第一条指令。此时保存真实返回地址并设置临时断点，可以直接观察 `main` 返回到运行时的那一刻，之后才捕获 `exit_group` 系统调用。完整输出在 `artifacts/D1/startup_gdb/stdout.log`，strace 的 `execve`、`write`、`exit_group` 在对应 stderr。

这说明程序的执行边界不等于 C 函数边界。`main` 的返回值交给运行时，运行时再安排退出；CPU 本身没有“看见 main 返回就自动关机”的规则。

最初的 GDB 脚本在默认隐藏 main 以上栈帧时使用 `finish`，报出“outermost frame”。后续使用实际返回地址观察，并保留失败记录；没有把那次未完成的 GDB 会话记为成功。

## 7. 不确定行为与原文更正：M015–M016

原文把 `f(i++, i++)` 用作“未指定行为”的示例。我们运行了原例并保留输出：本机 GCC 两次得到 `2,1`，Clang 两次得到 `1,2`。但这不能说明 C 标准只允许这两个结果。

**更正：在本实验使用的 C11 中，同一标量对象上的两次未排序副作用导致未定义行为。** N1570 §6.5 第 2 段给出规则，§6.5.2.2 第 10 段说明函数调用相关的排序关系。[原始标准草案](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)本身是 C11 草案，原页将其称作 C99 的文字也需要区分。

为了正确观察“顺序未指定但没有该 UB”，补充 [unspecified_order.c](src/unspecified_order.c)：两个函数分别输出标记并返回常量。两者调用先后未指定；最终参数仍为 1 和 2。这个例子没有对同一个标量进行未排序的两次修改。

[sequenced.c](src/sequenced.c)将两次自增放在分开的完整表达式中，两种编译器均输出 `1,2`。不要靠当前编译器“恰好从右往左求值”修复程序。

数组原例访问 `int a[10]` 的 `a[10]`，越过有效索引 `0..9`。普通运行输出不同的整数，只作为现象保留；用 UBSan 编译后，真实报告越界并非零退出，这才是错误对照。未定义行为即使连续输出同一个数，也不会因此变为定义良好。

## 8. 其余阅读与易错点

- token 分类与颜色渲染是两步。[colorize.py](colorize.py)完成小型着色练习：区分注释、字符串、关键字、标识符和数字；去除 ANSI 颜色后必须逐字恢复输入。字符串中的 `int` 和 `//` 不会误判为关键字或注释。另有 Clang 真实词法输出作观察；此练习不是完整 C 预处理器或编辑器。
- 当前 `CHAR_BIT=8`、`INT_MAX=2147483647`。C 的 `sizeof` 单位是 C 字节，其位数由实现规定；不能从 `sizeof(char)==1` 推出所有实现都是八位。
- `-Wall` 并不启用编译器所有可能的警告；`-Werror` 把已启用的警告提升为构建错误。这里的错误样例保留警告供观察，正式调试器代码则采用严格警告构建。
- 整数 ABI、指令语义和 Verilog 调度需要分别查对应规范；一次成功运行不能代替标准适用条件。

复验：在已配置的 WSL 中运行 `python3 /workspace/projects/ysyx_f_to_b/D/D1/run.py`。`--resume` 仅复用命令、输入和输出哈希都匹配的已通过记录；它不把过期结果算作新运行。
