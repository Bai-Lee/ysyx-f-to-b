# C3：从失败现象定位第一次错误状态

[C3 原文](sources/C3.md)明确本节暂无编程内容，只有课件和视频入口。因此本节对应 **C3-O001 背景记录，核心编程任务数为 0**。说明依据完整阅读的 v23.06 调试课件（原完整交付引用：`/workspace/YSYX_F_B_Archive/slides/markdown/2306/1dbf54f914088a36.md`），加上一组很小的真实 GDB 演示；未声称看完所有视频，也不代表正式课程学习掌握。

## 先说清楚“错”指的是什么

课件用三个层次区分故障传播：Fault 是代码中的缺陷，Error 是运行中已经偏离预期的状态，Failure 是对外可观察的不正确结果。缺陷可能暂未触发；错误状态也可能经过很多次函数调用后才变成崩溃或错误输出。

例如数组下标写错是一处 Fault，覆盖相邻对象是 Error，后来通过坏指针崩溃是 Failure。崩溃所在行可能只是受害者，所以仅盯着最后一条错误信息不够。调试要建立一条可检验的因果链：哪条需求应当成立、哪个状态第一次不成立、哪次操作造成了变化。

课件的“先怀疑自己的代码”适合作为工作次序，不是硬件、编译器和操作系统绝不会出错的定理。合理顺序是先固定输入、配置与版本，再用最小例子和独立证据排查；如果证据指向工具，也应保留复现材料，而不是凭直觉认定任何一方有错。

## 用什么工具缩短传播距离

| 目前能观察到什么 | 下一步 | 目的与限制 |
| --- | --- | --- |
| 编译/链接诊断 | 查看原型、类型、库顺序、生成的实际命令 | 先消除可静态发现的问题；零警告仍不等于功能正确 |
| 结果和预期不同 | 在边界增加断言、检查独立期望 | 将 Error 尽早暴露；断言条件本身也可能写错 |
| 某个变量被改坏 | GDB watchpoint、写入日志 | 找修改者；观察点受调试信息、作用域和硬件资源限制 |
| 程序运行很久才出错 | 用函数/设备 trace 缩小区间，再看指令和波形 | 先减少观察范围，再增加细节 |
| 行为正确但速度异常 | 记录工作量，再采样热点或测关键阶段 | 性能结论需要真实测量，不能由代码长短推断 |

ASAN、UBSAN 等工具能拦截部分内存或语言规则问题，但不会证明算法的答案正确；TSAN 适用于另外的并发问题。本章没有新跑这些工具或 perf，具体 CPU 性能留给 C4 的实际测量。对于自己的 RTL，可以把工具层次对应为程序结果 → DiffTest 提交差异 → 总线/访存 trace → 信号波形。

二分定位也需要前提。不能假定“某个检查点正确”就说明此前从未发生错误：状态可能被覆盖或暂时恢复。只有选择了足以区分目标错误、可重复比较的状态与检查点，缩小区间才有意义。随机种子、输入事件、延迟序列和构建版本都是复现的一部分。

## 实际 GDB 实验：总和 16 从哪里来

[sum_debug.c](sum_debug.c)顺序累加 `{1,2,3,4,5}`，独立期望的前缀和为 `1,3,6,10,15`。同一源码生成两个程序：正确版，以及仅用宏打开故意故障的版本。故障在第 4 个元素上额外加 1；测试的最终断言始终是 `result == 15`。

实测如下，见 [C3_experiment.json](../../reports/C3_experiment.json)和[完整 GDB 记录](results/watchpoint-transcript.txt)：

| 观察 | 正确版/预期 | 故障版实际 |
| --- | --- | --- |
| 最终总和 | 15，正常退出 | 16，原断言触发 SIGABRT |
| 第 1 次写入 | 1 | 1 |
| 第 2 次写入 | 3 | 3 |
| 第 3 次写入 | 6 | 6 |
| 第 4 次写入 | 10 | 11 |

先在 `sum_sequence` 入口设断点，再对 `running_total` 设置硬件监视点。前 3 次修改符合期望；第 4 次停止时，GDB 读到 `i=3`，从实际前后值算得本次增量为 `11-6=5`，而输入第 4 个元素是 4。此时已经抓到第一次偏离，无需等待程序在最后断言失败。

由此可分开描述三层证据：带故障的条件分支是 Fault；第 4 次累加得到 11 是 Error；最终输出 16 并触发断言是 Failure。正常版与故障版使用相同需求和断言，不能通过把期望改成 16 来修复。

实际 GDB 命令保存在 [watch_mutant.gdb](watch_mutant.gdb)，包含入口断点、监视点、调用栈、源码混合反汇编以及继续运行到 SIGABRT。这里只处理 5 次确定输入，手动列出继续次数便于阅读；复杂程序应改用条件、脚本或更高层的事件日志，不能靠人工重复敲几百万次 `continue`。

## 一个调试器自身的可见性边界

最初的 GDB 脚本试图在监视点停止后打印块内局部变量 `term`，实际收到 `No symbol "term" in current context`。这次失败保留在 `artifacts/C3/debug/gdb-watchpoint/attempts`。

原因是硬件监视点在写入已完成后停止，此处调试信息把当前位置关联到循环控制行，块内变量已经不在当前可见范围。最终脚本保存上一个可见的累加值，使用实际前后差值观察本次修改，并结合混合反汇编查看更新操作。没有删掉程序的断言，也没有把调试脚本的失败当成被测程序正确。

这也提醒我们：调试器显示的源代码行不一定就是刚刚造成修改的那一行；优化后变量还可能被移除、合并或只在某些指令范围内可见。遇到“看不见变量”，先区分作用域、调试信息与程序状态，再决定是否查看寄存器和反汇编。

另一个容易混淆的退出码是：Python 子进程记录中的 `-6` 表示程序被 SIGABRT 终止；GDB 批处理自身返回 0，只说明调试脚本按预期执行完毕。判断被测程序是否成功，还必须读取 inferior 的信号和输出。本实验同时断言 GDB 看到 SIGABRT，以及直接运行故障版确实被原断言拒绝。

## 用在后续 C 阶段的入口

总线改成多周期后，先明确何时才算提交一条指令，然后检查每个请求是否只被接收一次、回复是否归属正确请求、等待期间载荷是否保持。看到最终寄存器差异时，先用提交记录定位指令，再用对应地址和事务记录定位握手，不要一开始就打开所有周期的全部波形。

加载器问题可以先检查链接映像的 LMA/VMA 和节边界，再观察复制前后的小段内存。外设问题可以先核对访问地址、位宽、字节通道与副作用，再看设备内部状态。若数据被改坏，用一条具体地址的监视点往往比打印整个 RAM 更容易形成可检验的假设。

复验命令：

```powershell
wsl.exe -d YSYX-Linux -u ysyx -- python3 /workspace/projects/ysyx_f_to_b/C/C3/run_experiment.py
```

实验使用 `-O0 -g3 -fno-omit-frame-pointer`，顺序执行小型 GCC/GDB 任务；没有修改 NEMU、NPC 或旧阶段文件。命令与输入/输出/日志哈希完全匹配时才复用已有证据，复用不标作新执行。

完成范围仅是课件背景说明和这一个确定故障的定位。它没有覆盖所有优化等级、线程竞争、反向执行或 CPU 全输入正确性；C4/C5 仍须保留各自的真实正反例和资源边界。
